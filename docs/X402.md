# x402 merchant checkout

The merchant service supports x402 v2 `exact` payments using the official
`@x402/core`, `@x402/evm` and `@x402/hono` packages. They provide protocol handling,
EVM payment requirements, facilitator verification/settlement and the HTTP adapter.
The first supported checkout network is Base Sepolia (`eip155:84532`), with the
USDC asset and EIP-712 domain read from the SDK's default-asset registry.

## Configure

Install workspace dependencies with `bun install`. In `apps/merchants/.env`, set:

```dotenv
X402_ENABLED=true
X402_NETWORK=eip155:84532
X402_FACILITATOR_URL=https://x402.org/facilitator
```

The merchant still needs its existing signing keys, Arc RPC and factory
configuration to issue vault-bound signed activity quotes. Each merchant receives
payment at the address of its configured signing key, on Base Sepolia. A standalone
x402 payer needs Base Sepolia USDC. The agent proposer key is not used as a payer.

Set the API's `MERCHANTS_URL` to the same canonical base URL as the merchant's
`PUBLIC_URL`; the client checks the payment resource URL against that endpoint.
The facilitator must advertise x402 v2 `exact` support for the payment network.
The public facilitator currently advertises Base Sepolia, not Arc.

Restart merchants after configuration. Blank/false `X402_ENABLED` keeps the
existing vault payment flow for newly issued quotes. Each quote's payment mode is
persisted when it is issued. Complete in-flight bookings before changing modes.

## HTTP flow

1. `GET /catalog` includes an optional `payment` object on x402 merchants:
   `protocol`, CAIP-2 `network`, and USDC `asset` address.
2. `POST /quotes` accepts the existing activity, quantity, start time and vault
   request, and returns a signed quote. Prices stay in six-decimal USDC base units.
3. `POST /x402/bookings/:quoteHash`, with `Accept: application/json` and no payment,
   returns HTTP 402 and a base64-encoded JSON `PAYMENT-REQUIRED` header. This step
   does not reserve a booking or transfer money.
4. An independently authorized x402 payer creates a payment payload and retries
   that same endpoint with `PAYMENT-SIGNATURE`. The official SDK verifies it and
   settles it through the configured facilitator.
5. Only successful settlement publishes a booking, returns its JSON ticket and
   `PAYMENT-RESPONSE`, and enables `GET /x402/tickets/:id` with the booking code and QR.

The checkout request has no body: its price, recipient and activity come from the
stored signed quote identified by the path. New and unconfirmed purchases require
an unexpired quote. Ticket links are bearer links; keep them private.

Booking data and the settlement receipt are persisted in SQLite. Repeating the
exact original `PAYMENT-SIGNATURE` after a recorded successful settlement returns
the same ticket and receipt without settling again, including after quote expiry.
Only a hash of that header is stored. A different authorization for the same quote
is rejected once a payment attempt has been prepared.

If the process or facilitator connection fails after a payment may have settled,
the stored attempt remains pending. This slice does not automatically reconcile
that indeterminate outcome from chain receipts. Keep the original payment header
and reconcile the attempt before issuing another payment; do not create another
quote and authorization as an automatic retry. Pending attempts do not publish tickets.

## Context-aware agent integration

The integration extends the `b/B5-context-aware-discovery` booking path:

```text
saved destination/dates + web discovery
  -> relevant merchant catalog item
  -> signed quote
  -> unsigned x402 negotiation
  -> validated terms and participant-share draft
  -> payment_adapter_required
```

`MerchantClient.paymentRequirements()` decodes the x402 response, verifies the
quote signature/hash, and checks the resource URL, total, merchant recipient,
network and asset. It only performs an unsigned request. The agent receives
merchant terms inside its existing untrusted-data envelope.

For an x402 quote, `get_quote` returns payment requirements. `propose_purchase`
validates the participants and exact share sum, then returns an informational
draft with `submitted: false`, `paid: false` and `payment_adapter_required`.
It does not create a chain proposal, approval request, or confirmed booking.
The API proposal service also rejects x402 checkout through the legacy vault
proposal path, and the merchant watcher refuses vault fulfillment of x402 quotes.

## Remaining payment adapter

The Arc vault currently releases USDC when its merchant calls `fulfill()`. It
cannot authorize the Base Sepolia EIP-3009 payment required by this checkout.
The next integration must bind x402 requirements to participant approvals,
provide an authorized settlement mechanism, reconcile settlement and ticket
delivery, and define refunds. The agent must not use an independently funded
wallet as a substitute for that consent-enforcing adapter.

These x402 tickets are separate from `TripVault` proposal tickets, and the current
merchant catalog remains a mock supplier. Settlement confirms payment; it does
not independently prove that a real operator will honor the activity.
